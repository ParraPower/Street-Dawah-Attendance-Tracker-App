# AuthApp Documentation

## Project Overview

AuthApp provides authentication and authorization services for internal and external applications, such as the Attendance API. The application supports user authentication, machine-to-machine authentication, authorization, JWT token issuance and validation, and centralized identity management for the broader platform ecosystem.

The project follows a feature-based architecture that emphasizes clear separation of concerns, maintainability, testability, and rapid feature development.

---

# Setup and Installation

## Prerequisites

- Node.js 18+ (tested with Node 20)
- npm or yarn
- PostgreSQL 15+
- Docker and Docker Compose (optional)

## Installation

Clone the repository and navigate to the AuthApp directory:

```bash
cd AuthApp
```

Install dependencies:

```bash
npm install
```

Configure environment variables:

- Copy `.env.example` to `.env.local`
- Or copy `.env.example` to `.env.machine-local` for machine-specific development
- Update environment variable values

Required variables:

```env
DB_HOST=
DB_PORT=
DB_USER=
DB_PASSWORD=
DB_NAME=

PORT=

JWT_ISSUER=
JWT_DEFAULT_AUDIENCE=
JWT_EXPIRATION_TIME=
```

---

## Build

```bash
npm run build
```

This compiles TypeScript into JavaScript output within the `dist` folder.

---

## Running Locally

Ensure PostgreSQL is running and accessible.

Run database migrations:

### Windows

```bash
npm run migration:run:win
```

### Linux/macOS

```bash
npm run migration:run
```

Start development mode:

```bash
npm run start:dev
```

Or local environment mode:

```bash
npm run start:local
```

The API will be available on the configured port (default: `3000`).

---

## Running with Docker

Ensure Docker and Docker Compose are installed.

Start containers from the workspace root:

```bash
npm run docker:start -w AuthApp -- authapp <env>
```

Example:

```bash
npm run docker:start -w AuthApp -- authapp local
```

Alternatively:

```bash
docker-compose -f docker-compose.machine-local.yml up -d
```

Run migrations inside the container:

```bash
docker exec authapp npm run migration:run
```

The API will become available at:

```text
http://localhost:3000
```

Or whichever port is configured through environment variables.

## Deployment to Azure Web App

Build the project:

```bash

```

Ensure:

- Dependencies are installed
- `dist` directory is included
- Environment variables are configured in Azure

```bash

```

Or:

```bash

```

Set:

```env

```

# Architecture

AuthApp follows a **feature-based layered architecture**.

Each feature encapsulates its own:

- Domain layer
- Application layer
- Infrastructure layer
- Interface layer

Shared concerns are extracted into a central `shared` area.

```text
Feature
├── domain
├── application
├── infrastructure
└── interfaces
```

This structure promotes:

- Low coupling
- High cohesion
- Independent feature evolution
- Better testability
- Easier AI-assisted development

---

# Application-Layer Authorization Pattern

Authorization decisions belong within the application layer and not within controllers.

Controllers should only:

- Authenticate requests
- Translate JWT claims into actor contexts
- Invoke use cases
- Return HTTP responses

Use cases are responsible for enforcing authorization rules.

Example authorization service methods:

```typescript
canViewNonPublic()

assertCanCreate()

assertCanUpdate()
```

Authorization services may also enforce field-level permissions.

Example:

- Emir-or-higher can assign Emir values.
- Mudeer-or-higher can modify visibility settings.

Authorization failures should throw a dedicated authorization exception handled by the centralized error middleware and returned as:

```http
403 Forbidden
```

# Controller Framework Integration

## StreetDawahAppFramework

All APIs consume a shared framework library called:

```text
StreetDawahAppFramework
```

The framework is referenced in `package.json` as:

```json
{
  "dependencies": {
    "app-framework": "file:../StreetDawahAppFramework"
  }
}
```

All framework imports use:

```typescript
import ... from "app-framework";
```

Example:

```typescript
import { BaseController } from "app-framework";
```

---

## BaseController

Every controller in AuthApp must inherit from the framework's `BaseController`.

Example:

```typescript
import { BaseController } from "app-framework";

export class UserController extends BaseController {
    constructor(
        private readonly getUserUseCase: GetUserUseCase
    ) {
        super();
    }
}
```

Controllers should never implement common HTTP concerns themselves.

Instead, those concerns are inherited from `BaseController`.

Framework responsibilities include:

- Consistent HTTP response formatting
- Request validation helpers
- Standardized success responses
- Standardized error responses
- Logging integration
- Authentication helpers
- Authorization helpers
- Controller utilities
- Exception translation

All controllers throughout every API should inherit from `BaseController` to ensure consistency across the platform.

---

## Framework Usage Philosophy

The framework exists to centralize reusable infrastructure and cross-cutting concerns shared by all APIs.

Typical framework components include:

- Base controllers
- Middleware
- Error abstractions
- Logging abstractions
- Authentication infrastructure
- Authorization infrastructure
- Shared DTOs
- API response models
- Shared interfaces
- Common utilities

Features should leverage framework abstractions whenever possible instead of creating duplicate implementations.

# Bootstrap and Dependency Composition

## Overview

The `bootstrap` layer is responsible for application composition.

AuthApp intentionally uses an explicit Composition Root pattern rather than relying on automatic dependency injection frameworks.

Dependencies are instantiated manually and assembled together until a fully configured controller is produced.

The resulting controller instance is exported and registered within the application.

This approach makes dependency relationships extremely clear and is highly suitable for AI-assisted code generation.

---

## Dependency Construction Flow

Dependencies should be created from the lowest-level implementation upward.

Typical flow:

```text
Repository
    ↓
Domain Service
    ↓
Authorization Service
    ↓
Use Case
    ↓
Controller
    ↓
Export Controller
    ↓
Application Routes
```

Example:

```text
UserRepository
    ↓
UserDomainService
    ↓
UserAuthorizationService
    ↓
GetUserUseCase
    ↓
UserController
```

---

## Bootstrap Responsibilities

The bootstrap layer is responsible for:

- Loading configuration
- Initializing database connections
- Creating repositories
- Creating infrastructure services
- Creating domain services
- Creating authorization services
- Creating use cases
- Creating controllers
- Wiring middleware
- Wiring routes
- Exporting top-level application objects

---

## Example Composition

```typescript
const userRepository =
    new UserRepository(dataSource);

const userDomainService =
    new UserDomainService(
        userRepository
    );

const userAuthorizationService =
    new UserAuthorizationService();

const getUserUseCase =
    new GetUserUseCase(
        userRepository,
        userAuthorizationService
    );

export const userController =
    new UserController(
        getUserUseCase
    );
```

---

## Route Registration

Controllers that are composed during bootstrap are consumed by route registration.

Example:

```typescript
import { userController }
    from "./bootstrap/users";

router.get(
    "/users/:id",
    userController.getById
);
```

Controllers should never create their own dependencies internally.

Dependencies must always be supplied from bootstrap.

---

## Feature Bootstrap Organization

Each feature should own its own composition file.

Example:

```text
src/
├── bootstrap/
│
├── auth/
│   └── auth.bootstrap.ts
│
├── users/
│   └── users.bootstrap.ts
│
└── shared/
```

Each feature bootstrap should:

- Create repositories
- Create services
- Create use cases
- Create controllers
- Export the controller instances

The application should then consume only the exported controllers.

---

## AI Generation Guidance

When generating a new feature, AI should follow this order:

1. Domain entities
2. Repository interfaces
3. Domain services
4. DTOs
5. Authorization services
6. Use cases
7. Infrastructure implementations
8. Controllers inheriting from `BaseController`
9. Bootstrap composition
10. Route registration

Dependency direction should always flow inward:

```text
Controller
    → Use Case
        → Domain Service
            → Repository Interface
```

Infrastructure implementations satisfy repository contracts and are injected by bootstrap.

This convention must be followed for all future feature development.

Benefits include:

- Consistency
- Testability
- Reduced coupling
- Faster onboarding
- Predictable architecture
- High-quality AI-generated code
- Minimal prompting requirements

# Authentication Flow

## User Authentication

1. User registers.
2. User authenticates through:

```http
POST /auth/login
```

3. System validates credentials.
4. JWT is issued.
5. JWT is used for subsequent API requests.

---

## Machine Authentication

Client credentials authentication is supported for:

- Backend services
- Scheduled jobs
- Service-to-service communication

Clients authenticate using stored credentials and receive a JWT.


Typical workflow:

Generate migration:

```bash
npm run migration:generate
```

Run migration:

```bash

```

Revert migration:

